# Technisch register voor geo-standaarden

Content and publishing mechanism for **https://register.geostandaarden.nl**, the central
registry of technical artefacts (UML models, XML/GML schemas, Schematron rules, value
lists, visualisation rules and symbols) belonging to the Dutch NEN3610 family of
geo-information standards.

This repository replaces the webhook-based mechanism of
[technisch-register-2019](https://github.com/Geonovum/technisch-register-2019) and works
on the same principles as [docs.geostandaarden.nl](https://github.com/Geonovum/docs.geostandaarden.nl):
**the git repository is the source of truth for what is published.** Artefacts arrive as
automated commits or pull requests, are validated by CI and reviewed by a maintainer, and
are deployed to the webserver with rsync after merge.

## Environments

| Branch | Deployed to |
|---|---|
| `main` | https://register.geostandaarden.nl/ (production) |
| `develop` | https://test.register.geostandaarden.nl/ (test) |

## How publishing works

Source repositories (the information model repos listed in [`config/repos.json`](config/repos.json))
publish by creating a **GitHub release**:

1. The source repo's `publish-to-register.yml` workflow (see
   [`examples/source-repo-publish.yml`](examples/source-repo-publish.yml)) calls the
   reusable workflow [`publish-artefacts.yml`](.github/workflows/publish-artefacts.yml)
   in this repository.
2. That workflow checks that the source repo is listed in `config/repos.json`
   (the allow-list), and copies every directory of the release whose name matches an
   artefact type in [`config/descriptions.json`](config/descriptions.json) to
   `/{artefacttype}/{modelId}/` in this repository, replacing the previous content
   for that model.
3. * A **pre-release** is committed directly to `develop` → visible on the test
     environment within minutes.
   * A **release** results in a **pull request to `main`** titled
     *"Automated update from … to main"*. A register maintainer reviews and merges it;
     merging deploys to production.
4. On every push to `main` or `develop`, [`deploy.yml`](.github/workflows/deploy.yml)
   rsyncs the repository content to the webserver. Pull requests are validated first
   (XML well-formedness of changed files, configuration sanity).

As a fallback for source repositories that cannot run the caller workflow, and as a
recovery/resync tool, [`sync-releases.yml`](.github/workflows/sync-releases.yml) runs
daily (and on demand): it fetches the latest release of every configured source repo
and opens a PR whenever the register content differs.

## Website

The URL structure of the register is unchanged from the previous implementation:

1. *main index* — `/`, generated by `index.php`.
2. *cluster page* — `/{clusterId}`, generated by `index.php`. If a cluster contains one
   model this is directly an *index for a standard*.
3. *index for a standard* — `/{clusterId}` or `/{clusterId}/{repoId}`, generated by `index.php`.
4. *directory listing of an artefact type* — `/{artefacttype}/` (e.g. `/xmlschema/`),
   an Apache directory listing of a physical directory in this repository.
5. *directory listing of artefacts for a standard* — `/{artefacttype}/{repoId}/`,
   an Apache directory listing.

The PHP pages read their configuration from the local `config/*.json` files (no remote
fetches at request time). URL rewriting is handled by [`.htaccess`](.htaccess).

## Adding a new information model

1. Add the repository to `config/repos.json` (and, when it belongs to a cluster or is
   directly visible on the main index, to `config/cluster.json`) via a pull request.
2. In the source repository, add the caller workflow from
   `examples/source-repo-publish.yml` and make sure the `GH_APP_ID` /
   `GH_APP_PRIVATE_KEY` secrets are available (organisation secrets for Geonovum repos).
   If that is not possible, the daily `sync-releases.yml` run will pick the repo up
   instead — no changes in the source repo needed.
3. Structure the source repository with one directory per artefact type, named exactly
   as the keys of `config/descriptions.json` (`informatiemodel`, `xmlschema`,
   `jsonschema`, `shacl`, `gmlapplicatieschema`, `regels`, `waardelijst`, `wsdl`,
   `visualisatie`, `symbool`, `zipfile`). See the
   [guide for information model owners](documentatie/Handleiding%20voor%20beheerders%20informatiemodellen.md) [NL].
4. Create a pre-release to test, then a release to publish.

## For register maintainers

Full maintainer documentation (reviewing PRs, adding/removing models, editing website
texts, manual resync, server requirements) is in
[documentatie/Handleiding voor beheerders technisch register.md](documentatie/Handleiding%20voor%20beheerders%20technisch%20register.md) [NL].
In short:

* Review automated PRs before merging: check that the model id and artefact types in the
  PR description are what you expect, and that the diff only touches
  `/{artefacttype}/{modelId}/` directories of that model. **Merging deploys to production.**
* Configuration changes (`config/*.json`, `index.php`, `.htaccess`) are normal PRs and
  deploy the same way.

### Secrets used

| Secret | Used by | Purpose |
|---|---|---|
| `SSH_DEPLOY_KEY`, `SSH_HOST`, `SSH_USER` | `deploy.yml` | rsync to the webserver (same convention as docs.geostandaarden.nl) |
| `SSH_TARGET_DIR_PROD`, `SSH_TARGET_DIR_DEV` | `deploy.yml` | DocumentRoots of production and test |
| `GH_APP_ID`, `GH_APP_PRIVATE_KEY` | source repos calling `publish-artefacts.yml` | GitHub App with write access to this repository (same app as the docs.geostandaarden.nl flow) |

### Webserver requirements

* Apache with `mod_rewrite` and PHP, `AllowOverride FileInfo Indexes Options` (or `All`)
  and `Options +Indexes` for the DocumentRoot, so `.htaccess` and the directory listings
  work. No other server-side configuration is needed.
